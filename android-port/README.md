# Restarting PsychoVault for Android

I removed the experimental Capacitor/WebView Android source and started again using the extension-capable Chromium Android approach. The previously published preview APK is unchanged and does not have extension or Proton support. This folder does not yet produce a PsychoVault APK.

## Starting point

`engine/titanium/` contains the unmodified browser build and extension-host patches from Titanium Browser for Android at commit `5e9070a98b48f6b6cb239bf90b8718b91795b7c5`. Titanium is GPL-2.0; its licence and upstream README are included. Its Vanadium submodule is pinned to commit `0202b7badff99434822ba5e32e0d738792868455` in `engine/UPSTREAM.json`. Chromium, Vanadium and individual extensions have their own licences and notices. Review all redistribution obligations and the effects of combining this code before distributing a build.

The upstream source is a full Chromium Android browser, not a drop-in WebView library. It still contains Titanium branding and settings. It is not PsychoVault's interface and has not been built here. The source now stages the existing Dark Reader and Proton bundles for Chromium's unpacked extension loader, but neither extension has been installed or tested on Android. I must integrate the desktop-style interface and features and test extension installation rather than claiming the upstream code completes the port. See `EXTENSION-ENGINE-DECISION.md` for the engine comparison and outstanding work.

## Preparing source - not a build

On Linux or WSL2, `scripts/prepare-engine.sh /absolute/path/outside/the/repository` copies the pinned Titanium inputs and downloads the pinned Vanadium revision into a new workspace. It refuses to overwrite an existing path. The script does not fetch Chromium or build, sign, publish or run an APK. It needs Git, Python 3, Node.js and network access to GitHub. It also generates the packaged UI assets in the staged workspace. The default workspace is `~/psychovault-android-engine`; keep large dependencies and keys outside this Git repository.

The upstream `.gclient` fetches Chromium build dependencies and filter lists from external services when its build runs. The preparation script replaces the mutable Titanium extension hook in the staged copy with a version-pinned, SHA-256-checked download; the actual CRX download has not been tested in this sandbox. Other build inputs are not all pinned or reviewed yet. The upstream `build.sh` installs packages, modifies its checkout and expects signing credentials; do not run it as a PsychoVault release build. I need to replace that flow with a pinned, auditable build and release process before it is ready.

## Trusted Chromium host - source integration, not device-verified

I added a dedicated `chrome://psychovault-chrome` WebContents for the desktop-style chrome and a separate `chrome://psychovault-pages` origin for the PsychoVault new tab. The host creates regular and off-the-record chrome WebContents from the selected Chromium profile, attaches their ContentView to the activity, and keeps them outside the website TabModel. The activity installer creates the host after native/toolbar initialization and destroys its bridges, observers, delegates and WebContents on activity destruction.

The Java bridge is injected with an exact-origin matcher and a runtime method annotation. Every command also checks the live WebContents, its profile against the currently selected model, and its exact committed document path/profile query. Calls are marshalled to Chromium's UI thread. Website tabs do not receive the chrome bridge. Internal new-tab/settings/recovery documents receive a narrower handler scoped to their own page: navigation, settings reads, settings-page writes, vault/extension/recovery controls and opening a web link from Settings. They cannot activate/close other tabs or change chrome layout. Unsupported desktop operations return an error, and the principal unsupported controls are disabled rather than showing fabricated success.

The connected source covers new tab, tab selection/closure/move/reopen requests, address/search resolution, home, back, forward, reload, stop, find, zoom, pin/mute, private-tab switching and translation by opening Google Translate in a new tab. Tab-model and per-tab observers publish selected-profile snapshots. Closure remains a request: Chromium can still ask for confirmation. The resolver permits HTTP/HTTPS and the exact profile-matched PsychoVault new-tab/settings/recovery URLs, not arbitrary privileged schemes. Android back first dismisses chrome overlays through an OnBackPressedCallback before Chromium handles the page.

Settings persist per regular profile through a native SharedPreferences store keyed by the profile directory basename; incognito reads the original profile preferences and refuses durable writes. The allowlist now includes the blocker lists, workspaces, recovery snapshots, privacy headers/cookies/DNS/WebRTC/autoplay, spellcheck, CPU priority, tab sleep, vault, panic, rail services, page enhancements and interface mods. Unsupported desktop keys are still refused and disabled. Bookmarks/history use the existing IndexedDB library and only record committed, non-error, non-same-document primary-main-frame regular-profile navigations while remember is on.

Downloads use Chromium's real DownloadManager through a profile observer: GUID-based pause/resume/cancel/open/clear-history, progress and a derived speed estimate. The download folder can be chosen from the directories Chromium exposes on the device, and background completion/failure notifications are best-effort. A network limit is a duty-cycle pause/resume cap, not a kernel traffic shaper. Folder reveal is still not exposed. The blocker is a per-profile native URLLoaderThrottle using the bundled domain list plus custom/allow lists; it cancels with ERR_BLOCKED_BY_CLIENT and counts blocks per page/profile. DNT/GPC, referrer stripping and third-party cookie request headers are applied where the throttle can see them; this is not a leak guarantee. Workspaces are live Chromium tab groups, so switching keeps page state. Recovery snapshots are explicit additive SharedPreferences slots and never clear Chromium's own tab state. The vault reuses the desktop master-password format (scrypt N=16384/r=8/p=1, AES-256-GCM), adds CRUD/generate/copy/lock/auto-lock, encrypted .pvbackup export/restore, CSV import and migration recovery; there is no Android OS-keychain fallback or autofill yet. Performance uses real tab discard, renderer importance, fixed isolated-world media scripts and CopyFromSurface PNG snapshots saved through MediaStore; CPU/memory numbers are not fabricated. Extension management now imports ZIP/CRX through Android file pickers, shows a native permission prompt for CRX installs, reports Chromium load/uninstall results, persists imported extensions and restores bundled extensions. Proton opening is not a connection toggle and is not evidence of protection.

The chrome is a transparent overlay above Chromium's compositor. DOM-measured chrome regions receive touches; other touches fall through to the native page and notify the auto-hiding rail. The existing native top-control height remains the page's top inset; extra chrome height and an open side panel adjust compositor margins. The source keeps the desktop rail order: Performance/ad blocking, Proton, then Settings. This layout and touch path has unit coverage for its measurements, but has not been rendered or gesture-tested on Android.

`scripts/prepare-ui.cjs` still copies the real desktop renderer/CSS rather than creating a separate mobile product. It now adds the trusted bootstrap and extracts the copied new-tab script so the WebUI CSP can forbid inline scripts. The native asset source serves an explicit allowlist with no directory traversal or arbitrary APK-file access. The new-tab, settings and recovery pages are served from the page origin with separate role allowlists; the chrome origin cannot load them. The native asset allowlist is checked against the staged BUILD.gn file list by a regression test.

To generate UI assets alone: `node scripts/prepare-ui.cjs /absolute/path/to/new/output`. The target must not already exist. `prepare-engine.sh` generates these assets inside its external staged workspace and installs the Java/C++/GN integration through the existing source hook. None of this is an APK or a claim that Chromium compiles yet.

## Desktop feature verification

`scripts/audit-desktop-settings.cjs` inventories the 59 desktop default settings. The current source marks 57 as Android-source-implemented-not-device-verified, 1 (`extensions`) as extension-manager-source-not-device-verified, 1 (`settingsVersion`) as a desktop-internal migration marker, and 0 as missing host handlers. The last ten now have Android-adapted handlers: sitePermissions writes exact-origin HostContentSettingsMap rules; netLimit duty-cycles downloads; downloadDir chooses among Chromium's available directories; downloadNotify posts background notifications; spellDictUrl patches Chromium's bdic mirror URL (HTTPS only); spellUserWords syncs the profile custom dictionary; dismissedUpdate stores a dismissed Android release tag; mediaKeys registers an Android media session; mediaAutoPause pauses a service tab when another tab becomes audible; containers reopen tabs in named ephemeral OTR profiles. The inventories and adapter tests check coverage and contracts, not actual device functionality. Java/C++ have not been compiled against Chromium; no APK, extension install, Proton connection or leak test has run.

## Pinned extension build input

The staged engine source uses the upstream Titanium companion extension `v0.0.1` with its release SHA-256 recorded in `engine/psychovault/dependencies.json`. The download is size-limited and the hash is checked before the upstream bundler reads it. Unit tests cover successful verification, mismatches and size limits using synthetic data; staging the pinned Vanadium checkout and hook was also tested. I could not download the real GitHub release asset in this environment, so I have not verified the artifact bytes, bundle, Chromium signature handling or an APK. This companion extension is not Dark Reader or Proton.

## Library data code

The restart includes a bookmarks and history data module and an IndexedDB storage adapter. The desktop and internal-page bridge contracts can route their library calls through it, and it avoids recording private or non-remembered visits when the host supplies those profile facts. It serializes changes within one owner and does not replace good data on a write failure. It is now wired into the trusted chrome document and fed by host committed-navigation events. IndexedDB read-modify-write transactions keep two chrome windows from losing updates. Private history isolation and disk persistence still need a device test. No Android device has tested this code.

The staged GN configuration now uses `com.psychocore.psychovault` rather than Titanium's package or the former experimental preview package. That means it is a separate app from the earlier preview; it does not migrate that app's data. Package naming does not fix a signer mismatch, and signing, update compatibility and the reported install conflict still need device verification.

## Chromium tab controller source

`PsychoTabController.java` now runs behind the trusted host rather than being an unconnected activity factory. It retains the selected-model boundary and strict argument checks, resolves the PsychoVault new-tab URL for the current profile, and exposes navigation/tab snapshots to the host. The source installer registers the activity lifecycle hooks, Java files, WebUI configs and packaged assets. I checked installer anchors and Java syntax; I have not compiled Java/C++ against Chromium or tested navigation on a phone.

## Extension and VPN source

I stage the existing desktop Proton VPN and Dark Reader bundles as APK assets and load them through Chromium's unpacked extension path. Proton keeps its manifest key and extension ID; I do not sign a CRX or impersonate a store signature. Removal of a bundled extension is remembered per profile, and Restore brings it back. The trusted chrome can list, enable, disable, remove and open extension pages. The Proton button opens Proton's own popup; it does not fake a connect/disconnect result. The pinned Chromium source registers the `proxy` ChromeSetting transformer and wraps the Android system proxy service with `PrefProxyConfigTracker`, so Proton's `chrome.proxy` writes have a real path into the network context; the browser only reports "proxy configured", never "connected". Sign-in, proxy routing, `webRequestAuthProvider` credentials, DNS/WebRTC behaviour and failure handling still need a real device test. I will not call the Android browser VPN-protected before those pass.
