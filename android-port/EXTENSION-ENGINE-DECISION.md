# Android extension engine - research and decision

Research date: 1 November 2026; source status updated 2 November 2026. The source now contains general extension ZIP/CRX import, a native permission prompt, Chromium-reported load/uninstall results, bundled-extension staging and the broader feature handlers described in `README.md`. No Android extension install or device test has passed. Proton VPN is required in the Android port and remains unverified.

## What I need

I want PsychoVault's desktop interface adapted to a phone, installable Chrome extensions generally, the real Dark Reader extension, and Proton VPN as a default in-browser extension. The browser needs to remain shareable and support updates. Compatibility means the extension actually runs and its controls work - not just that an installer or API name exists. No Android browser can promise that every desktop extension works on mobile.

## Decision: Chromium Desktop Android, starting with Titanium for evaluation

The best starting point is an Android Chromium browser built with `is_desktop_android = true` and an extension host, using Titanium Browser's source and patches as the first candidate. It is a whole browser foundation, not an Android System WebView replacement library. I need to build PsychoVault on that foundation and port the PsychoVault UI and features onto it; I cannot simply add a Maven dependency or drop it into the existing Capacitor WebView.

Evidence: [Titanium's README](https://github.com/jqssun/android-titanium-browser/tree/5e9070a98b48f6b6cb239bf90b8718b91795b7c5) documents installation from the Chrome Web Store, other stores through its companion extension, and local CRX/ZIP. Its checked-in `args.gn` enables `is_desktop_android`; `patch.sh` modifies extension installation, the phone toolbar and popup handling; `build.sh` builds `chrome_public_apk`. I inspected those files at commit `5e9070a98b48f6b6cb239bf90b8718b91795b7c5` (30 October 2026). The latest stable release reported by GitHub was `v156.0.8078.79`.

This is a candidate, not proof that PsychoVault, Dark Reader or Proton works. In a [Dark Reader issue](https://github.com/jqssun/android-titanium-browser/issues/56), a user reported the popup seeing `about:` instead of the active page; the issue was later closed. Another [report](https://github.com/jqssun/android-titanium-browser/issues/333) describes file pickers closing extension popups on version 154. Both need retesting against the candidate build rather than assuming they still occur or were fixed.

A user reported Proton authentication loops; the Titanium maintainer later said the problem should be resolved in Chromium M154 builds ([issue #118](https://github.com/jqssun/android-titanium-browser/issues/118)). That is a useful change from the earlier audit, but it is not independent confirmation. Test Proton on a phone, with consent, including routing and leak/failure behaviour. A successful sign-in or green icon is not enough.

## Second candidate and alternatives

- [Bare Browser](https://github.com/BareBrowser/bare-browser/tree/4a9b2d9f96a636ba7c771caff0f36f3ce16e9453) is another open-source patch series for Chromium Desktop Android. GitHub identified its repo licence as BSD-3-Clause; its components have their own licences. I inspected commit `4a9b2d9f96a636ba7c771caff0f36f3ce16e9453` (30 October 2026). Its patches include signed-CRX installation and a bundled uBlock Origin mechanism. Its [2.0 beta release](https://github.com/BareBrowser/bare-browser/releases/tag/v2.0.0-beta.1) describes phone-friendly extension management and is marked pre-release. This is a credible fallback and comparison, but I have not established Proton support or tested it. I would compare both on the same device before locking the base.
- [GeckoView](https://mozilla.github.io/geckoview/javadoc/mozilla-central/org/mozilla/geckoview/WebExtensionController.html) is an embeddable engine with a real WebExtension controller; ordinary installed extensions require Mozilla signatures. Its Firefox extension ecosystem and APIs are not a guarantee that existing Chrome extensions work, so it is not the first choice for the stated Chrome-extension requirement.
- [Vivaldi Android 8.2](https://vivaldi.com/blog/vivaldi-on-mobile-8-2/) demonstrates that Chrome extensions on mobile are possible, and its [October snapshot](https://vivaldi.com/blog/android/android-8-3-4184-4/) announced Proton support. The vendor notes not all desktop extensions work on mobile. Vivaldi is useful as a behaviour comparison, not a proven redistributable source base for PsychoVault's own interface.
- The old Android System WebView foundation was not sufficient: it has no Chrome extension host. Injecting a dark-mode script or opening a separate browser is not general extension support or the requested integrated extension.

## What implementation actually entails

1. Freeze and review the chosen upstream commit, Chromium version, patches and dependency licences. Titanium's repo is GPL-2.0 according to GitHub; Chromium and bundled extensions have separate licences and notices. Review redistribution and corresponding-source obligations before shipping, including the planned combination with PsychoVault's existing code. Check any codec patents/licences as well. This is not legal advice.
2. Produce a reproducible unmodified baseline from source, without spending Actions usage until authorised. Review upstream patches rather than blindly inheriting them: for example, Titanium changes the extension-install dialog's touch filtering and external-extension safety handling. Decide whether PsychoVault should retain or replace each change.
3. Replace the WebView browsing foundation with the full Chromium browser. Connect or port PsychoVault's existing desktop-style chrome to actual Chromium tabs, actions, extension prompts and popups, preserving a trusted browser-UI/untrusted-page boundary. Electron APIs and the existing Capacitor plugin do not automatically transfer. The current simplified Android UI must be replaced or adapted to match the desktop interface on phones.
4. Implement a real extension manager: store installation and verified CRX/unpacked development paths as supported by the chosen host, permission/host-access prompts, install/remove/enable/update, popup and options pages, safe handling of private browsing, persistence across restart and extension failures. Clearly display permissions and origin; warn that extension code can read or change pages and that mobile compatibility varies. Test extensions beyond Dark Reader.
5. Bundle or install the actual Dark Reader extension with its existing MIT notice and source provenance, then test page transformation, per-site controls, popups, settings, updates and restart. The existing desktop copy is unpacked; Titanium's pinned bundled loader stages signed CRX files. Select a lawful supported distribution/update route and verify it retains the intended identity; do not invent Dark Reader's private key. A custom CSS darkener is not the extension.
6. Implement the required Proton extension as part of the port. The current desktop Proton bundle is unpacked. For default in-browser installation, investigate a verified upstream signed artifact or a supported first-party store/update mechanism, identity and update behaviour, licences and trademarks. A newly signed CRX has a different extension ID; it cannot impersonate the original. Do not claim VPN routing or leak protection before testing.
7. Reimplement/test browser features against the new host: navigation, private mode and storage isolation, native blocker, vault/autofill/backups, uploads/downloads, session recovery, settings and accessibility. Plan migration from the preview; simply using the same Android application ID does not migrate WebView data into Chromium profiles. An update also requires a compatible signing key and increasing version code. Never delete preview data without warning.
8. Maintain Chromium security updates and rebase patches continuously. Build the APK on a suitable runner and test on a real phone; source-check Actions are authorised, but an APK job must still meet the runner requirements. Verify install/update signatures and run extension installation, permissions, Dark Reader, navigation, restart, network and privacy tests. An API probe or build alone is not proof.

## Cost and build requirements

A $0 software route is a self-hosted Linux/WSL2 build on suitable existing hardware, optionally launched from a Windows `.bat`; the existing Windows repository path does not need to move. Chromium's [Android build instructions](https://chromium.googlesource.com/chromium/src/+/main/docs/android_build_instructions.md) specify x86-64 Linux, at least 8 GB RAM (more than 16 GB recommended), and at least 100 GB free disk, plus network access to Chromium, depot_tools and dependencies. Actual resources and build time need measurement. WSL2/Docker setup, hardware, electricity and internet are not guaranteed free or available.

GitHub's [standard public Linux runner](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists 14 GB storage despite free standard compute; that alone is not enough for Chromium's documented 100 GB requirement. Titanium's workflow defaults to a self-hosted runner, though it permits an `ubuntu-latest` input; that is not proof a standard runner will complete a current full build. Larger hosted runners or external storage can cost money. Do not assume either a free or paid hosted workflow works without measuring it.

At research time the sandbox had about 20 GB free and no configured Java or Android SDK; its outbound network also cannot fetch all Chromium build dependencies. No APK, Actions workflow, phone test, Dark Reader test, extension install or Proton traffic test was run during this investigation.

## What I have and have not established

I have identified an open-source Chromium-based foundation with an existing Android extension host as the closest match, plus a fallback and the migration work. I have **not** established that its APIs, default bundled extensions, UI integration, security properties or specific extension behaviour meet every PsychoVault requirement. The recommendation is conditional on a reproducible baseline and device compatibility tests, not a claim of completion.
