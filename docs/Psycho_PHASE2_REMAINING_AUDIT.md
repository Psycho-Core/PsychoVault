## Bottom line

Phase 2 is **not complete**, and its remaining work is not merely a request for the user to test. There are observable missing behaviors in the current engine, incomplete implementations of planned features, and insufficient independent coverage to decide whether all required behavior works. The developer can implement and automate much of this work; platform-dependent interactive tests are listed separately.

The exit gate has two requirements: (1) a golden-image suite covering the S052–S069 feature set, green on supported Windows, and (2) representative reference-UI CSS/DOM-contract fixtures rendering correctly. S071 is also a listed P2 step. It has a comparison **mechanism**; it has not demonstrated matching P3 views and is not proof of the two exit requirements. Full settings/new-tab implementation and full UI screenshot parity are P3/M2, not additional P2 gate conditions. Complete browser, HTML, CSS, SVG or Canvas standards conformance is not stated as the gate.

## Verification work needed to close the gate

1. **Make a feature-to-evidence matrix.** Break S052–S069's named requirements into testable behavior, link each to implementation, independent expected results, positive/negative/interaction cases, and Windows results. Mark gaps as code, tests, or an explicitly justified scope decision. The current historical S050 corpus JSON's hard-coded date and blanket deferrals are not a live status matrix.
2. **Expand the reference fixture contracts.** For `text-controls.html`, `flex-grid.html`, `scroll-position.html`, `images.html`, and `dynamic-dom.html`, specify expected DOM, geometry, paint and relevant interaction outcomes; obtain independent expected values/reference renders with documented viewport, fonts, resources and state. The existing selective assertions remain useful but do not prove each full fixture correct. Fix observed engine defects instead of blessing its output.
3. **Run the expanded suite on Windows.** Record the tested commit, run link, toolchain, input state, comparisons and outcomes. Keep exact or justified reviewed thresholds and preserve diffs. Current manual workflow dispatch was denied; the earlier scoped push-trigger workaround can validate a future run, then must be removed. A successful push run does not prove manual-dispatch access.
4. **Record platform-specific evidence separately.** Automated tests can exercise composition events, clipboard messages, DPR logic, damage and timing instrumentation. Real IME candidate placement, physical monitor changes and actual presentation/performance remain unproved by headless tests. Use an appropriate Windows environment or automation where possible; do not silently equate these with full UI screenshot parity or pretend a user test is currently blocking the code backlog.

## Suggested order of implementation

1. Build direct reference-contract blockers: DOM geometry/selector/data APIs, form-control state/painting (including the checked-flex defect), and reference-used CSS/text/layout cases. Add independent regression cases with each fix.
2. Complete the planned core layout/paint and interaction cases: flex/grid/box/positioning, scrolling/events, editing, images/SVG and viewport. Exercise combinations rather than only isolated properties.
3. Complete animation, incremental layout, retained compositing/telemetry, Canvas subset and font/DPI cases appropriate to the P2 plan. Collect actual performance/platform evidence rather than substituting metadata checks.
4. Complete the feature-to-test map, independently review representative reference fixtures, run Linux and Windows suites, and evaluate both exit-gate conditions. Full standards conformance and P3 UI parity should not be silently added as extra exit requirements.

No estimate is supplied: the required feature-level scoping and independent comparisons are incomplete, and the remaining work spans the engine, rendering, runtime input and Windows presentation paths.
